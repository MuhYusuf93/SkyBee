# M2 — Pengelolaan, persediaan, dan HPP

M2 menambahkan operasi gudang dan PIN pada fondasi M1. Tidak ada checkout/piutang/laporan penjualan/printer/notifikasi/Drive/restore ataupun alur consent final. Nama toko/PIN dibuat melalui Kelola jika belum ada; setelah itu kasir tetap terbuka tanpa PIN. Consent/legal onboarding tetap M6, sehingga build ini masih untuk pengembangan/review.

## Kepemilikan dan aliran

`AppServices` adalah composition dependency satu coordinator, ManagementService, InventoryService, SettingsService. Bukan AppProvider atau pemilik seluruh state. ManagementSessionProvider hanya status akses/busy/error/lifecycle; service tetap memegang otorisasi. InventoryProvider hanya filter/paging katalog, ProductDetailProvider hanya detail/halaman batch/submit layar, SettingsProvider hanya form. Master/picker/history memakai PagedController scoped. Semua daftar memakai keyset, 50+1 (picker 20+1), cache terbatas, tanpa OFFSET. Pergantian filter/tab membuang state usang; mutation commit diikuti refresh layar terkait.

Widget/controller tidak menjalankan SQL, KDF, rumus valuasi, atau membuka transaksi. InventoryService menangani master/operasi persediaan di satu dbTxn dan memeriksa akses sebelum pekerjaan serta sebelum commit. SQL tetap parameterized; identifier tabel hanya enum internal. Tidak ada token/PIN/data toko dicetak pada log aplikasi. Fixture test terpisah dan tidak di-seed pada production.

## PIN, sesi, dan pemulihan

- PIN tepat empat digit **String**, termasuk `0001`. Konfirmasi wajib, input numerik, tampilkan PIN default mati; tidak ada PIN awal/default produksi.
- [PinHasher](../lib/features/management/application/pin_hasher.dart): PBKDF2-HMAC-SHA256 **600.000** putaran, keluaran 256 bit, salt CSPRNG 32 byte. Algoritma/parameter disimpan bersama verifier. Work berjalan dalam isolate agar UI tidak diblokir. Pilihan parameter diperiksa pada [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), 12 Oktober 2026, serta API [cryptography](https://pub.dev/documentation/cryptography/latest/). Tidak menyatakan sertifikasi FIPS atau ketahanan PIN seperti password panjang.
- Pemulihan: CSPRNG 16 byte (128 bit), ditampilkan sebagai 32 karakter hex sekali setelah setup/rotasi. KDF memakai input prefix terpisah `pin:`/`recovery:` dan hanya verifier disimpan. Kode harus dicatat di luar perangkat. Rotasi selalu memeriksa PIN lama/kode pemulihan, membuat salt/verifier/kode baru dan mengunci sesi; kode lama tidak berlaku lagi. Untuk memperbarui kode pemulihan tanpa mengganti nilai PIN, verifikasi PIN lama dan isi PIN baru yang sama. Tidak ada reset tanpa verifikasi.
- Jika PIN dan recovery code hilang, tidak tersedia jalan pintas pengelolaan atau reset PIN. Pertahankan perangkat/database dan minta prosedur pemulihan data yang sah; reinstall/clear app data dapat kehilangan data. Ekspor/restore terproteksi akan tersedia M5. Kode recovery tidak dicetak otomatis/tidak dikirim ke pengembang.
- PIN empat digit hanya 10.000 kemungkinan dan KDF bukan enkripsi database. Penyerang yang memperoleh file/perangkat terbuka bisa mencoba offline; rate-limit aplikasi tidak melindungi salinan database yang dikuasainya. Gunakan kunci layar/perlindungan perangkat dan jangan bagikan recovery code. Dart tidak menjamin zeroization String di memori.
- Percobaan gagal tersimpan: dua pertama tanpa jeda; gagal ke-3 mulai 5 detik, lalu dua kali lipat hingga maksimum satu jam. PIN/recovery berbagi limit. Counting disimpan sebelum AppError dilempar (bukan rollback). Pembukaan ulang tidak menghapus limit; waktu efektif tidak mundur melewati last_attempt_at. Perubahan jam perangkat dapat membuat jeda lebih lama; tidak menjanjikan keamanan terhadap perangkat/root yang sepenuhnya dikuasai penyerang.
- Default lima menit **tidak aktif**, diukur Stopwatch monotonic agar perubahan jam kalender tidak memperpanjang sesi. Pointer/key activity serta edit dari keyboard lunak memperpanjang deadline; teks input tidak dicatat. Non-resumed/inactive/paused/detached mengunci dan menggagalkan unlock yang masih berjalan; kembali ke foreground tidak otomatis membuka sesi. Route/dialog pengelolaan memiliki gate sendiri karena dialog adalah Navigator overlay. PIN/recovery screen memang tersedia untuk verifikasi; recovery baru ditampilkan setelah verifikasi sah.
- Audit mencatat mode `management`, instalasi/action/reference/time; tidak menamai individu karena PIN dipakai bersama. Hash/password/kode recovery/customer payload tidak dimasukkan ke audit.

Pengukuran satu derive pada fixture **test debug**, bukan HP/rilis: Windows 2.469 ms, emulator Android 5.705 ms (log M2). Nilai ini dipengaruhi lingkungan dan bukan benchmark umum. Release/HP pengguna masih perlu diukur sebelum rilis; parameter tidak diturunkan untuk mempercepat test. Resolver memilih cryptography 2.9.0 dan timezone 0.11.1.

## Persediaan dan valuasi

- Products memiliki UUID stabil serta kode toko manual/otomatis UUID-based dengan unique constraint; collision menghasilkan penjelasan yang bisa ditindaklanjuti. Barcode kosong jadi NULL, teks mempertahankan nol di depan, konflik arsip mengarahkan pemulihan. Tidak ada supplier dummy. Kategori nullable; supplier tersimpan pada receipt, bukan wajib pada product.
- Penerimaan satu barang pada UI saat ini: quantity positif, harga beli wajib (nol eksplisit boleh), supplier/tanggal opsional. Receipt/item/batch/nilai/stok/history/audit/idempotency row disimpan atomik. Initial stock memakai jalur sama dengan history `initial`. operation_key dan canonical payload hash membuat retry identik tidak menambah stok; pemakaian key dengan payload berbeda ditolak.
- Nilai persediaan adalah total integer micro-rupiah skala 10^6; rata-rata adalah rasio nilai/jumlah **stok fisik**, termasuk stok belum dikeluarkan. Receipt menambah nilai quantity × unit cost, tidak membulatkan seluruh nilai menjadi rupiah. Display average dibulatkan half-up dalam presisi micro, lalu rupiah untuk tampilan. Harga jual tidak mengubah nilai/average.
- Pengurangan memakai share proporsional `round_half_up(value × remove / quantity)` dalam micro-rupiah. Pengurangan terakhir mengambil **seluruh nilai tersisa**. Tidak ada residu ketika stok nol. Contoh 10×8.000 + 10×10.000 menghasilkan average 9.000; helper removal 3 unit menghasilkan HPP 27.000. Helper bukan checkout/penjualan baru; penyimpanan snapshot sale akan M3.
- Stok opname: hitung fisik final, delta/alasan/waktu/nilai di ledger. Gain saat stok masih ada dinilai average saat ini; saat stok kosong harga beli wajib. Gain membuat batch tanpa tanggal yang dapat terlihat sebagai belum dicatat. Loss mengurangi batch bertanggal tertua dahulu (termasuk expired), lalu undated; nilai total loss dibagi ke ledger batch dengan residue pada baris terakhir. Bukan overwrite history/nilai bebas.
- Pengeluaran rusak/kedaluwarsa memilih batch dan quantity, alasan wajib. Quantity/nilai/batch/history berubah atomik; tidak dapat negatif. Expiry tidak otomatis menghapus/membuang unit fisik.
- Sale planning FEFO: dated earliest dahulu; undated terakhir, kemudian received_at/id tie-breaker. Batch habis diabaikan. Pada tanggal kedaluwarsa di **zona toko**, batch sudah tidak layak jual. CalendarDate valid yyyy-MM-dd disimpan tanpa UTC shift. Stok fisik/saleable/expired/undated berbeda. Window mendekati expiry adalah hari +1 sampai +5 dengan remaining >0; penayangan notifikasi tetap M5.
- Mematikan expiry monitoring ditolak ketika masih ada stok bertanggal, agar tanggal yang telah tercatat tidak diabaikan diam-diam. Tanggal baru dicatat pada penerimaan, tidak pada master. Disabled low-stock alert tidak mengubah stok; low stock memakai saleable `< min_stock` default 5.
- Reversal receipt terakhir hanya jika `stock_revision` sama dengan setelah receipt. Semua stok/valuasi mengubah stock_revision. Price/name edits hanya mengubah revision umum dan tidak menghalangi reversal persediaan. Reversal mengembalikan quantity/nilai exact sebelum receipt, menolkan batch receipt, menambah delta/history pembalik dan menjaga fakta awal. Setelah ada pergerakan stok baru, ditolak dan diarahkan ke opname/pengeluaran. Retry reversal identik idempotent.
- Arsip product stok >0 ditolak. Category yang masih dirujuk ditolak sampai barang dipindah. Supplier arsip tetap terbaca pada receipt lama. Restore product/master tersedia tanpa menghapus fakta. Undo harga/arsip selama lima detik mengharuskan expected revision, tidak menghapus perubahan lain dan membuat price_history baru bila harga dipulihkan. Semua operasi tetap memerlukan akses; tidak ada transaksi ditahan selama snackbar.

## Migration v3

V1/V2 tidak diubah. V3 menambah products.stock_revision, credentials.last_attempt_at, inventory_operations append-only dengan key/payload hash/before quantities/value/after revision/receipt/ref reversal, FK stock_history.inventory_operation_id, price_history.product_revision_after dan index master/batch/operation. Data v2 dipertahankan tanpa uninstall/drop-recreate. Nilai/revision historis lama tidak direkonstruksi menggunakan harga terbaru. Migration fixture v2→v3 dan regresi v1→current diuji di Windows/Android; tetap lakukan rekonsiliasi versi/data produksi bila nanti tersedia.

## Backup sistem sebagai prasyarat data sensitif M2

Karena M2 mulai menyimpan verifier PIN/data toko, manifest sekarang `allowBackup=false` dan XML mengecualikan seluruh domain storage untuk cloud backup serta device transfer. Ini opt-out keamanan minimal, bukan fitur backup/restore/consent M5/M6. [Dokumentasi Android](https://developer.android.com/identity/data/autobackup) menjelaskan default backup database dan variasi transfer OEM; aturan extraction eksplisit dipasang untuk API 31+. XML/build dapat diperiksa, tetapi transfer nyata semua OEM/versi Android belum diuji dan audit rilis masih M6. Jangan mengklaim ini enkripsi atau menjamin kontrol perangkat yang dikuasai pihak lain.

## Sisa tahap selanjutnya

M3 akan mengonsumsi FEFO/cost rules di checkout dbTxn, menyimpan HPP/harga snapshot, draft/recovery, pembayaran/piutang dan scanner/ranked search. M4 menambah koreksi finansial/laporan/rekonsiliasi menyeluruh/performa besar. M5/M6 tetap pending. Hasil/checkpoint perintah aktual ada di STATUS/VALIDATION-M2; requirement akhir yang memuat perilaku penjualan/notifikasi/legal masih partial/pending.
